# OWASP ASVS — tiered checklist

**Edition: ASVS 5.0.0** (May 2025 —
[github.com/OWASP/ASVS/tree/v5.0.0/5.0](https://github.com/OWASP/ASVS/tree/v5.0.0/5.0)) —
checked 2026-09-26. Requirement texts below are condensed; the ID is
authoritative — quote the full text from the standard when reporting.

This is a **triage excerpt: 60 of 345 requirements**, chosen for
risk-reduction leverage. It locates the weak chapters; it is not an
audit. A compliance claim at any level requires the full standard
(per-chapter markdown, plus CSV/JSON exports for tooling, in the repo
above).

## Levels

- **L1** — the minimum for anything in production: ~20% of
  requirements, the critical first layer of defense.
- **L2** — the target for most applications, especially anything
  handling sensitive data: all of L1 + L2 ≈ 70% of requirements.
- **L3** — highest assurance (banking, health, high-value targets):
  the remaining ~30%.

Pick the level from risk (data sensitivity, user expectations,
regulation), state it, then walk the checklist: an item fails if the
codebase cannot demonstrate it at or below the chosen level. Items
above the chosen level are recommendations, not failures.

## Checklist

### V1 Encoding and Sanitization

- [ ] **V1.2.1** (L1) Output encoding matches the context it lands in
  (HTML element/attribute, CSS, HTTP header, …).
- [ ] **V1.2.4** (L1) Database access uses parameterized queries or an
  ORM — no string-built SQL/NoSQL.
- [ ] **V1.2.5** (L1) OS calls use parameterized APIs or contextual
  command-line encoding — no shell string concatenation.
- [ ] **V1.3.2** (L1) No `eval()` or dynamic code execution (SpEL,
  etc.); where unavoidable, strictly sandboxed.
- [ ] **V1.5.1** (L1) XML parsers restrictively configured; external
  entity resolution (XXE) disabled.
- [ ] **V1.3.6** (L2) SSRF protection: untrusted URLs validated
  against an allowlist of protocols, domains, paths, ports.

### V2 Validation and Business Logic

- [ ] **V2.2.1** (L1) Input validated against expected structure —
  allowlists or strong rules, not blocklists.
- [ ] **V2.2.2** (L1) Validation enforced at a trusted service layer —
  client-side validation is UX, not security.
- [ ] **V2.3.1** (L1) Business flows process steps in order, same
  user, no step-skipping.
- [ ] **V2.4.1** (L2) Anti-automation controls against excessive calls
  (data exfiltration, quota exhaustion, DoS).

### V3 Web Frontend Security

- [ ] **V3.3.1** (L1) Cookies: `Secure` attribute plus `__Host-` (or
  `__Secure-`) name prefix.
- [ ] **V3.4.1** (L1) HSTS header on all responses, `max-age` ≥ 1
  year.
- [ ] **V3.4.2** (L1) CORS `Access-Control-Allow-Origin` fixed or
  validated against an allowlist — never reflected.
- [ ] **V3.3.2** (L2) Cookie `SameSite` set per cookie purpose (CSRF
  and UI-redress exposure).

### V4 API and Web Service

- [ ] **V4.1.1** (L1) Every response body carries a `Content-Type`
  (with charset) matching the actual content.
- [ ] **V4.4.1** (L1) WebSockets only over TLS (WSS).

### V5 File Handling

- [ ] **V5.2.1** (L1) Uploaded file size capped below
  denial-of-service territory.
- [ ] **V5.2.2** (L1) File extension checked against an expected-type
  allowlist (including inside archives).
- [ ] **V5.3.1** (L1) Untrusted uploads in public folders are never
  executed as server-side code.
- [ ] **V5.3.2** (L1) File paths built from internal/trusted data;
  user-submitted filenames sanitized (path traversal).

### V6 Authentication

- [ ] **V6.2.1** (L1) Passwords ≥ 8 characters (15 strongly
  recommended).
- [ ] **V6.2.4** (L1) New passwords checked against a
  breached/common-password list (top 3000 minimum).
- [ ] **V6.3.1** (L1) Credential-stuffing and brute-force controls
  (rate limiting, adaptive response) implemented as documented.
- [ ] **V6.3.2** (L1) No active default accounts (`root`, `admin`,
  `sa`).
- [ ] **V6.4.2** (L1) No password hints or security questions.
- [ ] **V6.3.3** (L2) MFA (or equivalent factor combination) required;
  at L3 a phishing-resistant factor.

### V7 Session Management

- [ ] **V7.2.1** (L1) All session-token verification happens in a
  trusted backend service.
- [ ] **V7.2.3** (L1) Reference tokens unique and generated by a
  CSPRNG.
- [ ] **V7.2.4** (L1) New session token issued on every (re)auth; the
  old one terminated.
- [ ] **V7.4.1** (L1) Logout/expiry actually invalidates the session
  server-side.
- [ ] **V7.5.1** (L2) Full re-authentication before changing sensitive
  account attributes (email, phone, MFA config).

### V8 Authorization

- [ ] **V8.2.1** (L1) Function-level access restricted to consumers
  with explicit permissions.
- [ ] **V8.2.2** (L1) Data-specific access checked per data item
  (IDOR/BOLA mitigation).
- [ ] **V8.3.1** (L1) Authorization enforced at a trusted service
  layer — never via controls a client can manipulate.

### V9 Self-contained Tokens (JWT & co.)

- [ ] **V9.1.1** (L1) Signature/MAC validated before any token content
  is trusted.
- [ ] **V9.1.2** (L1) Algorithm allowlist per context — `none` and
  algorithm confusion rejected.
- [ ] **V9.2.1** (L1) Validity window (`exp`/`nbf`) enforced at
  verification time.

### V10 OAuth and OIDC

- [ ] **V10.4.1** (L1) Redirect URIs validated by exact string match
  against a per-client allowlist.
- [ ] **V10.4.2** (L1) Authorization codes single-use.
- [ ] **V10.4.4** (L1) Clients restricted to the grants they need —
  implicit (`token`) and ROPC (`password`) not used.

### V11 Cryptography

- [ ] **V11.3.1** (L1) No insecure block modes (ECB) or weak padding
  (PKCS#1 v1.5).
- [ ] **V11.3.2** (L1) Only approved ciphers/modes (e.g., AES-GCM).
- [ ] **V11.4.1** (L1) Only approved hash functions for signatures,
  HMAC, KDF, random-bit generation.

### V12 Secure Communication

- [ ] **V12.1.1** (L1) TLS 1.2/1.3 only, latest version preferred.
- [ ] **V12.2.1** (L1) TLS for all client connectivity, no insecure
  fallback.
- [ ] **V12.2.2** (L1) External-facing services use publicly trusted
  certificates.

### V13 Configuration

- [ ] **V13.4.1** (L1) No source-control metadata (`.git`, `.svn`)
  reachable in deployments.
- [ ] **V13.3.1** (L2) Backend secrets live in a secrets-management
  solution (vault), not in code or config files.

### V14 Data Protection

- [ ] **V14.2.1** (L1) Sensitive data travels in body or headers —
  never in URLs or query strings.
- [ ] **V14.3.1** (L1) Authenticated data cleared from client storage
  (DOM, browser storage) on session end.
- [ ] **V14.2.7** (L3) Sensitive data has retention classification and
  scheduled/automatic deletion.

### V15 Secure Coding and Architecture

- [ ] **V15.2.1** (L1) No components older than the documented
  update/remediation time frames.
- [ ] **V15.3.1** (L1) Responses return only the required field
  subset — never whole data objects by default.
- [ ] **V15.3.4** (L2) Proxies/middleware forward the original client
  IP via trusted, non-spoofable fields.

### V16 Security Logging and Error Handling

- [ ] **V16.3.1** (L2) All authentication operations logged (success
  and failure, with factor metadata).
- [ ] **V16.4.1** (L2) Log output encoded against log injection.
- [ ] **V16.5.1** (L2) Unexpected errors return a generic message — no
  stack traces or internal details to the consumer.
- [ ] **V16.5.3** (L2) Failures fail securely and closed — no
  transaction proceeds past an error in its controls.

### V17 WebRTC (if used)

- [ ] **V17.1.1** (L2) TURN service cannot relay to
  special-purpose/internal IP ranges.
- [ ] **V17.3.1** (L2) Signaling server rate-limits and survives
  signaling floods.
